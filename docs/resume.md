## 项目描述（推荐版本）

**多 Agent 数字员工平台 · 企业尽调场景** `<起止时间待你填>`

**项目背景**：验证一个可量化的问题 —— Agent 的能力有多少来自架构、多少来自模型。
为使该问题可回答，平台**刻意只运行免费额度模型**：若用强付费模型产出好成绩，
架构贡献与模型贡献无法分离。主场景为 SEC 年报财务尽调，另接三个异构场景验证平台抽象。

**技 术 栈**：FastAPI / WebSocket / Redis / SQLAlchemy / Docker 沙箱 / MCP /
Function Calling（以 Code Execution 替代）/ Skill / Memory / SEC XBRL /
BM25 检索 / Ollama 本地推理 / Python 3.13 / pytest

**核心实现**

1. **Code Execution 执行基底**
   设计以"沙箱内写 Python"为 Agent 唯一动作的执行模型：工具编译为可 `import` 的模块
   而非注入 JSON schema，中间产物落盘、仅 stdout 回流上下文。该单一决策同时解决三个问题
   —— 上下文增长受"Agent 主动选择输出的内容"约束而非数据体量；第 40 步可读第 3 步产物；
   崩溃恢复是重读工作区而非重放对话（工作区即 checkpoint）。
   沙箱双后端（Docker `--network none` / 进程受限兜底），结果强制记录自身隔离级别；
   容器 10 项隔离属性由测试对活跃 daemon 逐条验证（非 root、内核级断网、只读根文件系统、
   内存 OOM、墙钟、禁装包、traceback 行号对齐）。
   无网络沙箱经**文件 RPC 桥**调用宿主工具，使宿主 broker 成为唯一可审计的出网收口。

2. **Context Ledger 上下文预算机制**
   设计槽位竞价式上下文分配：每步在 `窗口 − 输出预留 − 安全余量` 内重建 prompt（而非追加），
   六个槽位按硬下限 + 弹性系数 + 目标份额竞价，余量优先流向**最不弹性**的槽位。
   该两条规则共同保证检索记忆永不挤出操作契约 —— 这是"分层记忆"类主张最常见的失效模式。
   每次构造产出可审计的 `LedgerRecord`（各槽位配额/占用/淘汰项及原因），可直接输出 token 分配图。
   压缩仅在 **step 边界**且占用 > 70% 时触发（中途压缩会打断推理链），且在压缩不会实际缩短时中止。
   **实测**：单份 10-K 全文 61,206 tokens（超出 32k 窗口）；6k 窗口下移除压缩机制导致
   每步 token +15.7% 且额外驱逐 597 tokens，该效应在 12k 窗口以上消失 —— 机制的临界点由窗口扫描测出。

3. **零成本模型层**
   以"调用目的"而非模型名为路由键：`plan/code/judge` 走免费云端强模型，
   `extract/classify/rewrite` 走本地 Qwen3-8B（高频低难度调用不得消耗 plan 所需的日额度），
   judge 池与 actor 池不相交（模型不得评判自己的产出）。
   配额滑窗主动避让（429 靠撞出来代价是延迟 + 一个额度槽）、限流即降级不重试、
   请求指纹磁盘缓存 —— 后者是 8 组消融实验在免费额度下可行的决定性因素。
   付费 provider 默认不可达，仅 `strong-naked` 组显式开启。

4. **Agent MCP 工具接入**
   构建 MCP `tools/list` → Python 模块编译链路：MCP schema 转为沙箱内可 import 的函数
   （含必需参数排序、标识符净化），Agent 通过 `help()` 按需发现细节。
   工具选择由检索门控（IDF 加权覆盖率 + 绝对信息量双阈值，配停用词表 —— 小语料下 IDF
   无法自行折扣停用词）。
   **实测**：每步实付工具签名 188 tokens；同规模全量 JSON schema 为 1,456 tokens。
   且检索成本**与注册表规模无关**：320 个工具时全量签名 11,705 tokens、全量 schema 48,195 tokens
   —— 后者已超出整个 32k 窗口，这是工具编译方案相对 schema 注入的硬理由。

5. **Skill 体系与错误收敛**
   Skill 以 `SKILL.md` 指令包沉淀，两级结构（索引常驻 / 正文按步检索载入），
   被淘汰的正文降级为索引替身而非静默丢弃。
   错误收敛循环按**错误类别**而非消息文本识别重复（`name 'df' is not defined` 与
   `name 'tbl' ...` 是同一误解的重复，不是两个错误），反馈含异常类型、
   从 Agent 自身代码引回的失败行、按错误类的可执行提示，以及**被误用模块的真实签名重新注入**；
   升级有界：同类两次 → 更强模型，三次 → 人工，之后中止。

6. **A2A 协作与子 Agent 隔离**
   子 Agent 派生的目的不是并行而是**父级不必持有子级工作上下文**：子级获得全新 ledger
   与空历史、独立工作区子树，父级只回收摘要与产物路径、**永不回收子级 transcript**，
   文件通过共享工作区交接。成本按 Agent 维度独立归属（可回答"哪个子 Agent 烧掉了免费额度"，
   这是扁平 token 计数无法回答的）。派生深度设上限；记忆默认不继承（跨污染会让一个子 Agent
   的错误信念变成所有兄弟的错误信念）。

7. **服务层与运行观测台**
   FastAPI 28 个端点 + 每个 run 一条 WebSocket；读开放、写操作过 token、
   渠道 webhook 走平台签名。SQLAlchemy 持久化 Agent 声明、A2A 关系、会话与运行记录 ——
   **运行记录只是索引，不复制产物**（工作区与 trace 在磁盘上，否则恢复会变成合并而不是重读）。
   Redis 会话层带诚实的内存兜底并明示降级原因。
   渠道接入的**校验与幂等由路由统一强制**，适配器无法遗漏 —— 任何渠道都会在 200 慢响应时重投，
   而 Agent 运行天然慢，没有去重就会同一条消息起两个 run。
   同步 Agent 循环与异步 API 的桥接：有界线程池 + 每 run 事件队列，
   浏览器断开只丢事件不影响 Agent；取消是协作式的并**明确告知在下一个步边界生效**
   （持有容器的线程无法安全强杀）。
   前端是一个**运行观测台**而非管理后台：核心是每步的 token 槽位分配实时可视化 ——
   把"槽位竞价 + 硬下限"从一句话变成可以指着看的图。无构建步骤、无框架，
   因为整个项目都能离线零凭据运行，一个需要 npm install 才能渲染的看板会是唯一跑不起来的部分。

8. **自主 Agent vs 固化 Workflow 的量化对照**
   实现固化 DAG 对照组（`workflow-c`），与 Agent 组共享同一套语料、工具、指标与 harness，
   仅"由谁决定下一步"不同 —— 这使该对比成为测量而非争论。
   模型仅在一个节点被调用，且只为代码未能解决的字段提出科目名候选，
   随后由同一套确定性代码定位与换算（模型不读数字、不做算术）。
   **实测得出一个不需要模型即可确立的结论**：该组在 1,620 个字段槽中由代码解决 1,216 个（75.1%），
   404 个交给模型节点，其中 230 个真值确实存在 —— 即模型节点的可争取上限。
   由此该组存在 **0.738 的硬天花板**，且 **26.2 个百分点在结构上不可达**：
   模型节点只在"未答出"时触发，因此一个被自信答错的字段永不被复查。
   **固化管道能修补遗漏，修不了错误** —— 这是自主性取舍的具体形状。

9. **评测体系（项目信誉所在）**
   基于 SEC XBRL **半自动构造真值集**，这是 177 案例规模可行而人工标注只能到几十条的原因。
   映射层解决四类真实数据陷阱：一字段多标签（ASC 606 拆分）、`fy` 标注的是**填报年度**
   而非事实年度（FY2024 年报内含 FY2022 比较数且同标 `fy:2024`）、
   季度区间事实与年度同形（仅跨度可辨）、重述导致同期双值（后填报者胜且保留败者）。
   **实测**：177 案例（135 主集 + 42 held-out）、0 隔离、0 错误、
   资产负债表恒等式 177/177 通过且相对误差 0.0。
   语料按**会计难度**而非市值选样：12 个银行案例与 12 个保险案例无流动性划分，
   78 个案例无营业成本行 —— 这些缺失正是**拒答**指标的全部考点。

   四类自动指标，各自捕捉其余三者看不见的失效：
   数值准确率（三档容差，区分舍入与胡说）、
   **引用可验证率**（数字对但引文不在原文 = 猜的）、
   **计算一致性**（输入对而算错，以及算式自洽但输入编造）、
   **拒答正确性**（编造未披露字段）。
   L3 判断层配**可计算的客观骨架**：9 个跨年度信号由真值推导（营收增长而经营现金流下降、
   应收增速超营收、毛利率压缩…），各带重大性阈值，按召回率与精确率评分，
   judge 仅评判真正需要判断的部分并报告其自身 κ 校准。
   **实测**：118 个年度对、126 个信号、**39% 为零信号案例**（考察 Agent 是否编造发现）。

## 平台抽象的可验证陈述

> 接入新场景只允许新增 `AgentSpec` + 工具模块，不允许修改 runtime 任何一行。

由测试强制：AST 检查断言无场景继承或 monkey-patch runtime 类，
且三个场景端到端跑通同一个 `Agent` 类。四场景异构性覆盖不同压力
（极限上下文/数值精度、schema 上下文/生成 SQL 执行安全、子 Agent 隔离/来源溯源、
沙箱文件系统/外部测试预言），其中两个场景完全不需要宿主 bridge —— 证明 bridge 是
平台提供的选项而非强加的依赖。
